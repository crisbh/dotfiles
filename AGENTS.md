# dotfiles

Personal dotfiles for macOS (Homebrew) and Fedora (dnf), deployed into `$HOME` with GNU Stow. Durable facts only: how things are built, checked and laid out, and what not to touch.

## Layout and deployment

- The repo root is the stow package: every file not matched by `.stow-local-ignore` is symlinked into `$HOME` by `install.sh` (`--no-pkgs` to only re-stow, `--yes` to answer every prompt). After a merge, `dotfiles-update` brings a machine up to date: pull, stow, crontab, tmux reload, `dotfiles-doctor`. Repo-only files (docs, manifests, CI, `.gitignore`) must be listed in `.stow-local-ignore`, or they land in `$HOME`.
- `.gitconfig` sets `core.hooksPath` to `~/.config/git/hooks` (`.config/git/hooks/` here) for every repository: `commit-msg` rejects agent attribution, then runs the repository's own `commit-msg`. Other hooks in `.git/hooks` do not run while it is set, and `pre-commit install` refuses to install.
- Git identity (`[user]`) and machine-specific settings (credential helpers, signing keys) go in `~/.gitconfig.local`, which `.gitconfig` includes and the repo does not track. `~/.gitconfig` is a link into the repo, so installers that run `git config --global` (Git Credential Manager, for one) write into the working tree: move their lines to `.gitconfig.local`.
- Packages: `Brewfile` (macOS, shared by every Mac) and `packages-fedora.txt` (Fedora), both installed by `install.sh` and both kept by hand. To update the Brewfile, run `brew bundle dump --force --no-describe --file=<scratch file>` and copy over the lines for what was installed on request; a full dump also lists dependencies. Leave out per-machine state (`link: false`) and mark every tap `trusted: true` (Homebrew ignores untrusted taps). `brew bundle` carries on past failures, so `install.sh` then runs `brew bundle check` and repairs what it reports (links, `--adopt` for apps installed by hand, npm and cargo packages), and `dotfiles-doctor` warns about anything still unsatisfied.
- `.zshrc` sets `DOTFILES_OS` (`macos`/`linux`) and `$VAULT` (the notes vault; `~/notes` on Fedora) and puts `scripts/` on `PATH`. Aliases live in `.config/.aliasrc`.
- Cron: one template, `crontab.in`, for every machine. `dotfiles-cron` renders it (`{{PATH}}`, `{{VAULT}}`, `{{SCRIPTS}}`, `{{BASH}}`, `{{OWNER}}` placeholders; lines prefixed `macos:` or `linux:` only on that OS), `--diff` compares it with the installed crontab and `--install` installs it. Never install it with `crontab` directly. `dotfiles-doctor` warns when the installed crontab differs.
- The task pipeline and vault tools (`todo`, `vault`, `vault-sync`, `day`, `zet`, `note`, `todo-pomodoro`, `watch-todos`) live in their own repo, [vault-tools](https://github.com/crisbh/vault-tools), installed as a uv tool into `~/.local/bin` (`uv tool install $VAULT_TOOLS_URL`, set in `scripts/lib/common.sh`; `install.sh` installs it with the packages, `dotfiles-update` upgrades it, `dotfiles-doctor` checks it). The dotfiles keep the integration: Neovim keymaps, `crontab.in`, `repos`, the doctor and the old names as wrappers. Changes to the task formats or commands belong there, with a matching change here when a name changes.
- The vault is shared between machines through its GitHub repo by `vault-sync`, which every machine runs: only `0-tasks/`, `0-zettelkasten/` and `templates/` are shared (allow-list `.gitignore`, template in vault-tools' `vaultops.py`); `diary/` and the rest stay local to each machine; after pulling it runs `todo collect` and `todo done`, so completed tasks reach every machine. On macOS `$VAULT` is in iCloud, so the Macs share one folder (including its `.git`): only the Mac with `~/.vault-owner` runs `vault-sync` and the task cron jobs (the crontab lines test for it, `vault-sync` refuses without it). Exactly one Mac must have that file.
- `repos` tracks unsynced work across machines: it searches the folders in `scripts/repos.conf` and caches the repositories with work not on a remote in `~/.cache/repos-status`. Cron refreshes the cache every 15 minutes and notifies at 16:00 and 18:00; the top of `.zshrc` (above the Powerlevel10k instant prompt, which flags later output) and the catppuccin module `.tmux/plugins/catppuccin-tmux/custom/repos.sh` read it.
- `.claude/` holds only the tracked Claude Code config (`settings.json`, `CLAUDE.md`). `~/.claude` must be a real directory with those two files linked in, never a folded symlink to the repo, or credentials, history and sessions land in the working tree: `install.sh` creates it (and migrates a folded link) before stowing, and `dotfiles-doctor` checks it. The same goes for `~/.config` (tools keep state and tokens there), `~/.ssh` (private keys) and `~/.tmux` (plugins): `install.sh` creates them, and clones tpm and the catppuccin theme first, since the repo only adds `custom/claude.sh` to the theme. Entries in `.stow-local-ignore` for root-only files are anchored (`^/CLAUDE\.md$`) so they do not also skip `.claude/CLAUDE.md`.
- espanso reads `~/.config/espanso` (stowed from `.config/espanso`; `espanso path` confirms it), not `~/Library/Application Support/espanso`. Snippets with personal details go in `match/personal.yml`, which is gitignored (the repo is public) and created by hand on each machine; `base.yml` shows its format.
- Claude Code is installed by the `claude-code` cask on macOS and by the native installer (`~/.local/bin/claude`, self-updating) on Fedora; its tmux hooks need `jq`.

## Neovim (`.config/nvim`)

- Kickstart-based, lazy.nvim, one spec per file in `lua/plugins/`. Needs Neovim 0.11+.
- nvim-treesitter and nvim-treesitter-textobjects are on their `main` branches: parsers are installed by `lua/plugins/treesitter.lua`, highlighting is started from a `FileType` autocmd, and text objects are mapped explicitly there.
- LSP: mason-lspconfig v2 enables installed servers automatically; `lua/plugins/lspconfig.lua` only layers capabilities and per-server settings via `vim.lsp.config`. Tools Mason must install are listed there (`mason-tool-installer`).
- Formatting: conform.nvim with format on save (not for C/C++/CUDA); `<leader>tf` toggles it.
- `lua/git-marks.lua` adds git status letters to Telescope file lists.
- `~/Projects/.python-shims/` holds symlinks named after Python packages whose repo folder has a different name; pyright and `gf` search it.

## Scripts (`scripts/`)

- Everything in `scripts/` is on `PATH`, so names must not clash with existing commands or aliases (check `.config/.aliasrc`).
- Split by role: Python for code that parses or rewrites file contents (`arxiv2bib`); bash for glue around other tools (`wt`, `commit`, `push`, `sq`, `tp`, `repos`, `dotfiles-doctor`, ...).
- Bash scripts start with `#!/usr/bin/env bash`, a header comment that `--help` prints (`usage`), `set -euo pipefail`, and `source "${DOTFILES:-$HOME/.dotfiles}/scripts/lib/common.sh"` (`die`, `warn`, `confirm`, `tmpfile`/`tmpdir`, `require_vault`, colours, `VAULT_TOOLS_URL`; it also loads `lib/portable.sh` for macOS/Linux differences). vault-tools keeps its own copies of both files: keep them in step. `dotfiles-doctor` and `repos` deliberately omit `-e` and check exit codes explicitly.
- Python: standard library only, Python 3.9+ (macOS's system python3), no `__pycache__` in the repo (`sys.dont_write_bytecode`).
- Old names are kept as thin wrappers because Neovim keymaps and muscle memory use them: `todo-collect`, `todo-mark-done`, `todo-add-tags`, `todo-backup`, `todo-add-task`, `vault-ls`, `vault-stats`, `vault-broken-links`, `vault-orphans`, `vault-check-sensitive`, `vault-clean-empty`, `generate-diary-index` (all run the vault-tools command from `PATH`), `listen`, `pusha`. Do not remove them.

## Checks

- `scripts/check` runs shfmt (`-i 2 -ci`), shellcheck and the Python tests; `scripts/check --fix` reformats. CI runs it on PRs touching `scripts/` (`.github/workflows/scripts.yml`).
- Single test: `cd scripts/tests && python3 -m unittest testarxiv.ParseTest.test_refs` (module, class or method).
- Tests are in `scripts/tests/` (stdlib `unittest`, files named `test*.py` without underscores). The task and vault tests, and the fixture vault, are in vault-tools. Never run tests or experiments against the real `$VAULT`.
- `dotfiles-doctor` checks a machine against what the dotfiles expect (tools, links, cron, vault).
- Install test: `scripts/tests/install-check.sh` installs the committed dotfiles as a new user on a fresh Fedora container and checks the result (stow, real home directories, zsh, tmux, Neovim, tests, `dotfiles-doctor`). CI runs it in a Fedora container on PRs touching the install, shell, tmux or Neovim files (`.github/workflows/install.yml`); `dotfiles-test` runs it locally with podman in the Lima VM `dotfiles-test` (needs `lima`; the first run boots the VM, about 10 minutes). Run it after changing `install.sh`, `packages-fedora.txt`, `.zshrc` or the stow layout. Never run `install-check.sh` on a real machine.
